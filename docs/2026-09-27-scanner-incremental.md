# 세션 목록 API 성능 — 스캐너 증분 파싱 (v0.9.3, 2026-09-27)

## 문제

세션 목록 API 는 모든 jsonl 의 메타(cwd·제목·모델·마지막 시각·줄 수…)를 스캐너가 뽑아 내려준다.
캐시 키가 (mtime, size) 라 **활성 세션은 바뀔 때마다 파일 전체를 다시 파싱**했다. 이 세션(63.7MB,
12,654줄)이 매 턴 자라므로 원격 UI 의 20초 폴링·알림 클릭·새로고침이 첫 호출마다 2.9초 걸렸다
(2026-09-15 알림→탭 점프 e2e 에서 발견, 크로스체크로 자기 회복 다음 사이클로 확정).

## 설계

- **접기(fold)**: 메타의 모든 필드가 "처음 값"(cwd/slug/gitBranch/version/started_at) 아니면 "마지막 값·
  카운트"(custom/ai 제목, agent-name, last_model, last_ts, 대화형 마커 수, 줄 수)다. 따라서 파일 끝에 붙은
  줄만 이어서 접으면 처음부터 읽은 결과와 **동치**다. `_Fold.feed(line)` 하나가 전체·증분 공용.
- **캐시**: 경로 → (mtime, size, meta, fold). fold 는 오프셋(완성된 줄의 끝)과 오프셋 직전 64바이트 서명을 갖는다.
- **판정**: 같은 mtime·size → 캐시. 자랐고 서명이 같으면 → 오프셋부터 새 바이트만 접기. 그 외(축소·교체·앞부분
  재작성) → 전체 재파싱(Gemini·Codex: mtime 만 믿지 말 것).
- **부분 줄**: 개행 없는 마지막 줄은 접지 않고 오프셋도 그 앞에 둔다 — claude 가 쓰는 중인 줄을 반만 읽지 않는다.
- **명시 무효화**: jsonl 을 재작성하는 우리 코드(경로 갱신 `update_cwd`, 세션 이사 `move_session`)는
  `scanner.invalidate(path)` 를 부른다. append-only 전제가 깨진 파일을 증분으로 접으면 옛 상태 위에 새 줄이 얹힌다.
- 읽기는 바이너리 1MB 청크 → 텍스트 모드 줄 반복보다 전체 파싱 자체가 9배 빨라졌다(부수 효과).

## 검증

- 단위 5건: 여러 차례 append(부분 줄 → 완성 포함) 뒤 증분 == 전체, 축소/앞부분 재작성 폴백, invalidate,
  무변경 시 파일을 열지 않음, 6MB 성능(증분 < 0.2s, 전체의 1/5 미만). 기존 scanner·lifecycle 테스트 무회귀.
- 실파일(이 세션 63.7MB): 전체 0.31s(이전 2.9s) → 17KB 자란 뒤 **증분 4ms**, 전체 파싱과 동치.

## 남은 것

- 목록 API 는 여전히 매 호출 전 파일 stat + 라벨 로드 + `claude agents --json`(10초 캐시) — 세션 수백 개면 수십 ms.
- 프로세스 재기동 후 첫 목록은 전부 전체 파싱(캐시가 메모리) — 필요해지면 메타 캐시를 디스크에.
