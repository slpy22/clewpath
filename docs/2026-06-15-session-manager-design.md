# Design: Claude Code Session Manager (006_session_manager)

Generated by /office-hours on 2026-06-15
Status: APPROVED
Mode: Builder

## Problem Statement

로컬 PC에 Claude Code 세션이 22개 프로젝트에 걸쳐 쌓여 있는데, 이를 관리할 방법이 없다. 특히 (1) 세션을 다른 PC로 그대로 옮기는 것, (2) 너무 많아진 세션을 정리(삭제)하는 것, (3) 과거 세션을 검색/열람하는 것, (4) 세션의 작업 폴더를 바꾸거나 재개하는 것이 불편하다.

세션은 `~/.claude/projects/{경로인코딩}/{uuid}.jsonl` 형태로 로컬에 투명하게 저장되어 있어 외부 도구로 관리 가능하다.

## What Makes This Cool

**세션 포터빌리티.** 기존 도구(claude-code-trace, claude-code-viewer 등 5개+)는 거의 다 읽기 전용 뷰어다. 이 도구의 차별점은 **세션 생명주기 관리** — export/import로 세션을 다른 PC로 통째로 옮기고, 작업 폴더까지 함께 번들링하여 새 PC에서 이어서 작업할 수 있게 한다. "이 세션을 집 PC에서 회사 PC로 옮긴다"가 한 번의 export/import로 된다.

## Constraints

- 로컬 단독 실행 (클라우드 없음)
- Windows 11 + Git Bash 환경 (크로스플랫폼 고려하되 우선 Windows)
- Python 3.11 + FastAPI (기존 seed_agent 스택 재사용)
- 브라우저 기반 로컬 웹 UI (네이티브 앱 아님)

## Premises (확정)

1. **관리가 핵심, 뷰어는 기본.** 뷰어/검색은 이미 시장에 흔하다. 차별화는 export/import/폴더변경/삭제 같은 세션 생명주기 관리에 둔다.
2. **방어적 설계.** Claude Code의 JSONL 포맷은 공식 문서가 없고 버전마다 바뀔 수 있다. 스키마를 가정하지 않는다. 알려진 핵심 필드(`type`, `cwd`, `timestamp`, `message`, `uuid`)만 가볍게 파싱하고, 모르는 필드는 그대로 보존한다. 원본 jsonl은 절대 손실 없이 보존.
3. **Export는 세션 + 작업 폴더를 함께 번들.** 단, 작업 폴더는 `.gitignore`를 존중하여 스마트 번들링(node_modules, .venv 등 제외). 용량 폭증 방지. import 시 작업 폴더는 새 PC 경로로 재배치하고 cwd를 일괄 재지정한다.

## 세션 저장 구조 (조사 완료)

```
~/.claude/
├── projects/{경로인코딩}/           # 예: F--021-3-AX----- (슬래시/공백/한글 → 하이픈)
│   ├── {uuid}.jsonl                 # 세션 전체 대화 (핵심, 매 줄에 cwd 필드)
│   ├── {uuid}/                      # 사이드체인/서브에이전트 폴더
│   └── memory/                      # 프로젝트 메모리
├── session-env/{uuid}               # 세션 환경 정보
├── todos/, plans/                   # 작업 상태 (세션 연관)
└── shell-snapshots/                 # 셸 스냅샷
```

핵심 데이터는 `projects/{경로}/` 에 집중. jsonl 매 메시지에 `"cwd"` 필드 존재 → 폴더 변경/import 시 일괄 치환 대상.

## Approaches Considered

### Approach A: Python + FastAPI + 로컬 웹 UI (채택)
- 요약: FastAPI 서버 + 브라우저 UI. `python -m session_manager` 로 띄우고 localhost 접속.
- 효과: jsonl 파싱, zip 번들, 폴더 이동, .gitignore 처리 전부 Python 표준 라이브러리로 해결. 기존 스택 재사용으로 가장 빠름.
- Reuses: seed_agent의 FastAPI 패턴, Python 인프라 경험

### Approach B: Tauri 네이티브 앱
- 가볍고 단독 실행파일. 단 Rust 학습 곡선, 파일시스템 로직을 Rust로 재작성해야 함. 개발 느림.

### Approach C: Electron
- 친숙하나 무겁고(~100MB+) 빌드 복잡.

## Recommended Approach

**Approach A.** "나를 위한 도구를 빠르게"라는 목표에 정확히 맞는다. 파일 조작이 핵심인데 Python이 가장 유리하고, FastAPI를 이미 능숙하게 쓴다. 네이티브 앱 느낌이 필수가 아니므로 로컬 웹 UI로 충분.

## 기능별 핵심 로직

| 기능 | 핵심 |
|---|---|
| **목록 조회** | `~/.claude/projects/` 스캔 → 프로젝트별 세션 목록 + 메타(크기, 메시지 수, 최종 수정일) |
| **뷰어** | jsonl 매 줄 파싱 → user/assistant/tool 메시지를 읽기 좋게 렌더. 모르는 type은 raw 표시 |
| **검색** | jsonl grep (키워드) + 파일 mtime (날짜) |
| **통계** | 파일 크기 합, 메시지 수, (가능하면) 토큰 집계 |
| **삭제** | `{uuid}.jsonl` + `{uuid}/` + `session-env/{uuid}` + 연관 todos 삭제. 삭제 전 확인 |
| **폴더 변경** | `projects/{기존}/` → `projects/{신규}/` 이동 + jsonl 내 `cwd` 일괄 치환 |
| **Export** | `{uuid}.jsonl` + `{uuid}/` + memory + manifest.json(원본경로/cwd/메타) + 작업폴더(.gitignore 존중) → .zip |
| **Import** | .zip 해제 → manifest 읽기 → 새 PC 경로로 cwd 치환 → `projects/{경로}/` 배치 → 작업폴더 재배치 → 재개 안내 |
| **재개** | `claude --resume {uuid}` 호출 (또는 안내 출력) |

## Open Questions

- 토큰 통계: jsonl에 usage 필드가 일관되게 있는지 검증 필요 (없으면 메시지 수만 표시)
- Import 시 작업폴더 충돌(이미 같은 경로에 파일 존재) 처리 정책 — 덮어쓰기/병합/새폴더 중 택
- UI 프레임워크: 순수 HTML+JS vs 가벼운 프레임워크(Alpine.js 등) — 구현 시 결정

## Success Criteria

- 22개 프로젝트의 모든 세션을 한 화면에서 목록 조회 가능
- 세션 하나를 export → 다른 PC에서 import → `claude --resume`로 대화 이어서 시작 성공
- 큰/오래된 세션을 골라 안전하게 삭제 (원본 손실 없는 확인 절차)
- 세션 작업 폴더 변경 후 정상 동작 (cwd 치환 검증)
- 원본 jsonl은 어떤 작업에서도 손상되지 않음

## Next Steps (빌드 순서)

1. **scanner.py + 목록 UI** — 세션 스캔 → 프로젝트별 목록 + 메타. (가장 먼저, 모든 기능의 기반)
2. **viewer.py + search.py** — jsonl 뷰어 + 검색. 방어적 파싱.
3. **stats.py** — 크기/메시지 수 통계.
4. **lifecycle.py (삭제)** — 연관 파일 포함 안전 삭제 + 확인 절차.
5. **lifecycle.py (폴더 변경)** — 폴더 이동 + cwd 치환.
6. **exporter.py** — .zip 번들 (세션 + manifest + 작업폴더 .gitignore 존중).
7. **importer.py** — .zip 복원 + cwd 재지정.
8. **resume.py** — claude --resume 연동.

각 단계마다 원본 백업/검증을 우선한다. 파괴적 작업(삭제/이동/치환)은 dry-run 먼저.

## What I noticed about how you think

- "export, import는 그 세션을 그대로 다른 pc로 옮겨 가려고 할 때 유용할 것 같아" — 단순 백업이 아니라 **이동성**을 핵심 가치로 본 게 날카롭다. 기존 뷰어 도구들이 다 놓친 지점이다.
- Premise 3에서 "작업폴더도 함께"를 고른 것 — 대화 기록만 옮기면 반쪽짜리라는 걸 본능적으로 알았다. 완전한 이전을 원하는 건 도구를 실제로 쓸 사람의 감각이다.
- 개발 전에 /office-hours로 점검부터 하자고 한 것 — 만들기 전에 "이미 있나? 함정은?"을 먼저 묻는 습관. 이게 시간을 아낀다.
